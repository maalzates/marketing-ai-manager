01 El repositorio

Una regla estructural

Todo el backend vive en src/app/Modules/. app/Http/ solo guarda el Controller base de Laravel, app/Models/ solo User hasta que exista el módulo de autenticación, y app/Services/ no se crea nunca.

Qué se expone

  • 80 y 443 — nginx
  • 22 — SSH
  • Nada más. UFW deniega el resto.

Qué NO se expone

  • MySQL, atado a 127.0.0.1
  • Redis, solo en la red interna
  • Grafana, atado a 127.0.0.1

Diferencias reales entre dev y producción

Añade scheduler, restart: unless-stopped y healthchecks. Quita node (los assets se compilan durante el despliegue) y mailpit. Monta php.prod.ini, con opcache activo y validate_timestamps=0: el código no se relee del disco, por eso cada despliegue reconstruye las cachés.

05 Dos ficheros de entorno

Los lee software distinto. Confundirlos es el error más común al montar el servidor.

.env.docker — lo lee Docker Compose

Con qué credenciales se crea MySQL, y qué dominio sirve nginx.

  • APP_DOMAIN — elige el certificado TLS
  • MYSQL_DATABASE / USER / PASSWORD
  • MYSQL_ROOT_PASSWORD
  • GRAFANA_ADMIN_*

src/.env — lo lee Laravel

Con qué credenciales se conecta la aplicación, y todo lo demás.

  • APP_KEY, APP_URL, APP_DEBUG
  • DB_* — deben coincidir con los de arriba
  • REDIS_HOST=redis
  • Credenciales de plataforma (OAuth, LLM)

La trampa

MySQL solo lee sus variables al crear el volumen. Cambiar MYSQL_PASSWORD en .env.docker sobre una instalación que ya existe no cambia la contraseña real del usuario: hay que hacer ALTER USER dentro de MySQL y actualizar src/.env. Si los dos ficheros divergen, la aplicación no puede entrar en su propia base de datos.

Ninguno de los dos está en git. Las credenciales por cuenta (BYOK: Apify, tokens de Meta y Google del usuario) no van en ningún .env: viven cifradas en las integraciones de cada cuenta y se resuelven en tiempo de ejecución.

Por qué reset --hard y no pull

Un rebase o un force-push en main dejaría un pull atascado en un conflicto a las tres de la mañana. reset siempre converge.

Por qué reiniciar los workers

queue:work mantiene el código viejo en memoria mientras viva el proceso. Sin el reinicio, el despliegue lleva código nuevo a la web y código viejo a la cola.

El servidor no necesita Node: los assets se compilan en un contenedor desechable. Un servidor nuevo se prepara una sola vez con scripts/setup-production.sh. Detalle completo —DNS, TLS, secretos de Actions, rollback, backups— en deployment.md.
