Una regla estructural

Todo el backend vive en src/app/Modules/: 703 ficheros PHP repartidos en 20 módulos. app/Http/ solo guarda el Controller base de Laravel, app/Models/ solo User, y app/Services/ no se crea nunca.

02 Los veinte módulos

Cada clase del backend pertenece a uno. Un módulo posee una porción del dominio y ofrece al resto de la aplicación exactamente una cosa: un Service. Ni un repositorio, ni un modelo, ni un cliente.

La estructura interna, idéntica en los veinte

app/Modules/{Módulo}/
├── Application/ DTO/ · Services/ · Jobs/ — la lógica de negocio
├── Domain/ Contracts/ · Enums/ · Exceptions/ — el vocabulario
├── Infrastructure/ Persistence/ · Repositories/ · Clients/ — lo que habla con fuera
├── Presentation/ Http/ · Tools/ — las puertas
└── {Módulo}ServiceProvider.php ata los contratos y registra las tools

El contrato vive en el módulo que pregunta

Cuando un módulo necesita una respuesta que otro tiene, declara él la interfaz y el otro la implementa y registra el binding en su propio provider. Declararla junto a la implementación parece igual de razonable y produce un ciclo cada vez: durante la construcción inicial aparecieron dos, Strategies↔Experiments y Brands↔Strategies, invisibles fichero a fichero.

05 Contenedores · producción

docker-compose.prod.yml, en /var/www/marketing-ai-manager. Misma imagen que en desarrollo; cambian el php.ini, el entorno y qué se expone.

Qué se expone

  • 443 y 80 — nginx
  • 22 — SSH
  • Nada más. UFW deniega el resto

Qué NO se expone

  • MySQL, atado a 127.0.0.1
  • Redis, solo en la red interna
  • Grafana, atado a 127.0.0.1

Diferencias reales entre dev y producción

Añade scheduler, restart: unless-stopped y healthchecks. Quita node (los assets se compilan durante el despliegue) y mailpit. Monta php.prod.ini, con opcache activo y validate_timestamps=0: el código no se relee del disco, y por eso cada despliegue reconstruye las cachés.

06 Dos ficheros de entorno

Los lee software distinto. Confundirlos es el error más común al montar el servidor.

La trampa

MySQL solo lee sus variables al crear el volumen. Cambiar MYSQL_PASSWORD en .env.docker sobre una instalación que ya existe no cambia la contraseña real del usuario: hay que hacer ALTER USER dentro de MySQL y actualizar src/.env.

Ninguno de los dos está en git. Lo que hay en src/.env son credenciales de plataforma: identifican a la aplicación y las pone una sola vez quien despliega.

Las credenciales de usuario no van en ningún .env

La key de Apify, la de Anthropic, OpenAI o Gemini, y las conexiones OAuth de Meta y Google identifican a una persona, no a la aplicación. Se introducen por el onboarding, viven cifradas en la tabla integrations con APP_KEY, y se resuelven por cuenta en cada petición o trabajo. No hay key de reserva, ni key compartida, ni «la del admin cuando el usuario no tiene».

Un cliente con la key de una cuenta nunca se cachea en un singleton: serviría a todas las cuentas con la key de una.

El recorrido completo —qué consola externa da cada valor y en qué orden— está en SETUP.md.

07 Del push al servidor

Pull request

Actions · CI: Pint · PHPUnit contra MySQL · build de frontend

Merge a main

dispara Deploy to production

Job test

la misma CI, sobre el commit de merge

ssh al VPS

scripts/deploy.sh, solo si test pasó

Un build en rojo nunca llega al servidor

Los tests corren en el pull request, y el merge vuelve a correrlos sobre el commit resultante — el árbol que se mergea no siempre es el que probó la PR, y es el mergeado el que se despliega. ssh depende de ese job con needs, así que un rojo corta el deploy. concurrency: production-deploy hace que dos merges seguidos se encolen en lugar de competir.

Qué hace deploy.sh

  1. Sincroniza el código — git fetch + reset --hard. Un rebase o un force-push dejaría un pull atascado en un conflicto a las tres de la mañana; reset siempre converge.
  2. Levanta el stack — compose up -d --build, y espera a que MySQL responda.
  3. Dependencias PHP — composer install --no-dev --optimize-autoloader.
  4. Assets — npm ci && npm run build dentro de un node:22-alpine desechable, así el servidor nunca necesita Node.
  5. Migraciones — artisan migrate --force.
  6. Datos de referencia — artisan db:seed --force. Los dos roles y las entradas de conocimiento no son datos de ejemplo: sin ellos el primer login muere con Role not found. Todos los seeders son firstOrCreate.
  7. Cachés — optimize:clear primero: cachear encima de una caché vieja vuelve a hornear los valores antiguos.
  8. Reinicia los workers — queue:work mantiene el código viejo en memoria mientras viva el proceso.
  9. nginx, el último — restart nginx. Resuelve app una sola vez, al cargar su configuración; si el contenedor vuelve con otra dirección, todo responde 502 con php-fpm perfectamente sano.
  10. Health check — curl https://APP_DOMAIN/up, diez intentos. Si no responde, el job termina en rojo.

Un servidor nuevo se prepara una sola vez con scripts/setup-production.sh. Detalle completo —DNS, TLS, secretos de Actions, rollback, backups— en deployment.md.
