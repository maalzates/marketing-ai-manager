01 Un núcleo, varias puertas

HTTP no es la única forma de entrar. Las herramientas del asistente de chat, los jobs programados y —en el futuro— un servidor MCP son adaptadores de entrada: puertas finas que traducen su formato a un DTO y llaman al mismo Service.

  petición HTTP      tool_use del chat      job programado       llamada MCP (futuro)
        │                   │                     │                    │
        ▼                   ▼                     ▼                    ▼
   FormRequest          clase Tool            clase Job          handler Mcp
   valida + toDTO()     valida + DTO          construye DTO      reusa las tools
        │                   │                     │                    │
        ▼                   ▼                     ▼                    ▼
   Controller ──────────────┴──→ Service ←──────┴────────────────────┘
                                    │
                                    ▼
                        Repository  /  ApiClient      las únicas capas que tocan
                                    │                 Eloquent o HTTP saliente
                                    ▼
                             Model  /  API externa

Las puertas no deciden

Validan su entrada, construyen un DTO y delegan. Un if sobre presupuestos o veredictos dentro de una puerta está en el sitio equivocado.

Los invariantes están en el centro

Topes de gasto, aprobaciones, guardarraíles: se aplican una vez, en el Service, y valen para todas las puertas automáticamente.

Validar ≠ invariante

Cada puerta valida su formato. Que un presupuesto no supere el tope no es validación: es lógica de dominio, y nunca vive en una puerta.

Entre módulos

Un módulo puede depender del Service de otro. Nunca de su repositorio, su modelo ni su cliente. Alcanzar App\Modules\Otro\Infrastructure\… es como un monolito modular se convierte en un monolito normal con carpetas de más.

03 Una petición, de punta a punta

  1. nginx recibe. /api/* y los ficheros de public/ los resuelve él; todo lo demás va a php-fpm.
  2. Ruta. routes/api.php para JSON. routes/web.php es un único catch-all que sirve app.blade.php: a partir de ahí manda el router de Vue.
  3. FormRequest. prepareForValidation() transforma, rules() valida, toDTO() mapea. Un toDTO() que transforma es un bug.
  4. Controller. Una línea: pasa el DTO al Service y envuelve lo que vuelva en $this->response.
  5. Service. Las reglas. Comprueba, orquesta, y lanza excepciones de dominio con ?? throw.
  6. Repository. La consulta, siempre filtrada por account_id. Devuelve Collection, Model o LengthAwarePaginator. Nunca un array.
  7. Respuesta. Un único envoltorio, para acierto y para error.
{ "result": { "id": "camp_1" }, "errors": [] }

{ "result": [], "errors": { "message": "Campaign not found", "status_code": 404 } }

en un fallo de validación, además:
{ "result": [], "errors": { "message": "…", "status_code": 422,
                            "fields": { "name": ["The name field is required."] } } }

En el frontend, el flujo es el espejo: Componente → Store → Repository → axios → /api. Los repositorios desenvuelven data.result; el interceptor de bootstrap.js aplana el error a un único Error con status y errors. axios solo se toca en los repositorios.

04 Errores y logs — una sola línea por fallo

  Repository / Client            los ÚNICOS dos sitios con try/catch
        │
        │  throw CampaignCreationFailedException::wrap($e, context: [...])
        ▼
  Service                        no captura — deja pasar
        │
        ▼
  Controller                     no captura — deja pasar
        │
        ▼
  ┌────────────────────────────────────────────────────────┐
  │  bootstrap/app.php                                    │
  │                                                        │
  │  report()  → Log::log( $e->getLogLevel() ,             │
  │                        $e->getMessage(),               │
  │                        $e->getContext() )              │
  │                                                        │
  │  render()  → ExceptionRenderer  →  envoltorio de error │
  └────────────────────────────────────────────────────────┘

La excepción decide su nivel

StatusNivel
400, 422info
resto de 4xxwarning
5xxerror

Un código fuera del rango HTTP (un driver de MySQL lanza 1045) se normaliza a 500.

Qué se le devuelve al llamante

  • ClientException — su clientMessage y sus extras. Es culpa del llamante y puede arreglarlo.
  • ApiException — su mensaje, que siempre lo ha escrito una persona.
  • Cualquier otra — mensaje genérico, salvo con APP_DEBUG.

Nadie llama a Log:: a mano

Loguear y lanzar produce dos entradas del mismo fallo, con dos niveles y dos formas, y la manual se escribe aunque la excepción se acabe manejando más arriba. El detalle crudo del proveedor va en context, que solo llega a los logs; nunca al cuerpo de la respuesta.

ExceptionRenderer cubre también lo que lanza Laravel —validación, auth, un 404 del router— así que el frontend nunca se encuentra dos formas distintas de error.

05 Llamar a una API externa

YouTube, Instagram Graph, Meta Marketing, Apify, el LLM. Todas siguen la misma forma.

  Service
     │  $this->client->getChannel($id)
     ▼
  YoutubeClient extends ApiClientAbstract      endpoints como constantes
     │
     │  catch (ApiCallFailedException) → throw YoutubeClientException::from…
     ▼
  ApiClientAbstract                            verbos, JSON, traducción de errores
     │                                            contexto: método, URI, opciones,
     ▼                                            status y cuerpo decodificado
  GuzzleClientFactory                          timeouts y cabeceras compartidos
     │
     ▼
  proveedor

Dos tipos de credencial, dos mecanismos

TipoIdentifica aDe dónde saleCómo se liga
Plataforma
OAuth client, App id, DB		 la aplicación config/services.php leyendo env() singleton en el provider del módulo
Cuenta · BYOK
Apify, LLM, tokens del usuario		 el usuario cifradas en las integraciones de la cuenta *ClientFactory->forAccount($id), por petición o job

Nunca cachear un cliente de cuenta

Ni en un singleton, ni en una propiedad estática, ni en estado compartido del contenedor. Un singleton serviría a todas las cuentas con la clave de un usuario. Resolver por cuenta, usar, descartar.

env() no se llama nunca fuera de config/: en producción la configuración está cacheada y devuelve null.

06 El asistente propone, la persona ejecuta

El invariante más importante del sistema, y está en la arquitectura, no en el prompt.

  el LLM pide una mutación
        │
        ▼
  PauseCampaignTool                    una tool de mutación
        │
        │  NO existe camino de código de aquí al Service que ejecuta
        ▼
  ProposalService::create()            persiste una Proposal y la devuelve
        │
        ▼
  la propuesta aparece en la interfaz
        │
        │  la persona pulsa aceptar
        ▼
  POST /api/v1/proposals/{id}/accept    puerta HTTP que el LLM no conoce
        │
        ▼
  CampaignPauseService                 ahora sí, ejecuta

Por qué así

Un modelo se equivoca; un if no. El tope de gasto y la exigencia de aprobación son validaciones duras en el backend, no instrucciones del tipo «no gastes más de X».

Qué significa al escribir código

Una tool de mutación importa ProposalService. Si te encuentras importando el Service que ejecuta desde una tool, has roto el invariante — no hay una versión aceptable de eso.

Las tools de lectura sí ejecutan directamente: consultar métricas o listar campañas no cambia nada ni cuesta dinero.

07 Aislamiento por cuenta

La aplicación es multi-cuenta desde el primer día, así que no hay un «luego lo añadimos».

  toda tabla de usuario lleva  account_id
        │
        ▼
  la cuenta viaja en el DTO          no en una variable global, no en la sesión
        │
        ▼
  el Repository siempre filtra
        │
        ▼
  ->where('account_id', $filters->accountId)

Ningún Service, Tool ni Job alcanza datos de otra cuenta. Las pruebas lo afirman explícitamente: crear dos cuentas, pedir desde una, comprobar que lo de la otra no aparece.

08 Cómo se prueba

Solo feature tests. No existe tests/Unit.

Toda prueba entra por una puerta real y recorre la cadena entera hasta MySQL.

  petición HTTP   →  ruta  →  controller  →  service  →  repository  →  MySQL
  job despachado  →  handler  →  service  →  repository  →  MySQL
  comando artisan →  service  →  repository  →  MySQL

Un unit test con el repositorio mockeado afirma que un Service llamó a un método. Sigue en verde con la consulta rota, la ruta sin registrar y el binding sin declarar — las tres cosas que de verdad se rompen.

Contra MySQL, no sqlite

phpunit.xml solo sobrescribe DB_DATABASE (marketing_ai_testing); el resto de la conexión viene de .env. Así las columnas JSON, los ENUM, las colaciones y el modo estricto se comportan como en producción. MigrationsTest falla si alguien vuelve a sqlite.

Qué se puede falsear

Solo lo que sale de la máquina: HTTP externo (MockHandler, Http::fake()) y el LLM. Nunca un repositorio ni un Service — mockear lo que estás probando es como una suite en verde esconde una funcionalidad rota.

Redis, la red y las credenciales del LLM se quedan fuera: caché en array, cola sync, mailer en array.

09 Cómo se trabaja

Todo cambio —funcionalidad, arreglo o investigación— empieza por una spec y termina por documentación al día.

  Fase 0   context.md   análisis; se lee el código antes de proponer nada
              │  ← el usuario aprueba
  Fase 0b  plan.md      qué fichero se toca y para qué
              │  ← el usuario aprueba
  Fase 1   implementar  dev y tester en paralelo
              ▼
  Fase 2   pruebas      si fallan, no se pasa de aquí
              ▼
  Fase 3   QA           revisor de solo lectura + pint
              ▼
  Fase 4   simplificar  y volver a pasar las pruebas
              ▼
  Fase 5   guide.md  +  sincronizar documentación
                             incluidos estos dos canvas

Las specs se escriben en español y viven en spec/AAAA-MM-DD-{tipo}-{caso}/, fuera de git. El detalle está en CLAUDE.md; las reglas de código, en .ai/ai-guidelines.md.

La última casilla

Un cambio no está terminado hasta que Mapa del proyecto y este canvas siguen diciendo la verdad. Una documentación que contradice al código es peor que no tenerla: se confía en ella y está mal.
